Project 01 · DoStock

수혜주 리서치 시, 뉴스에 안 나오는 2~3단계 공급망 기업을 놓치는 문제 해결

DART 공급망 그래프 기반 수혜주 추천 서비스

2025.12 – 현재2인 팀● 직접 운영 중
담당파이프라인 설계 · 그래프 모델링 · MCP 에이전트 개발 · 풀스택
흐름도
입력·출력핵심 처리데이터 저장
① 수집 파이프라인Airflow 자동 실행 · 데이터를 쌓는 흐름
② 추론 파이프라인FastMCP 도구 + Claude Code · 쌓인 데이터로 판단하는 흐름
문제 원인
  • 상한가 종목의 배경을 찾을 때 뉴스에 직접 언급된 기업만 보인다.
  • 원자재·부품 업체처럼 2~3단계 떨어진 수혜주는 시장이 반응하기 전까지 드러나지 않는다.
해결 과정
  • DART 사업보고서에서 공급망 관계를 추출해 Neo4j 그래프로 구축, [:SELLS_TO*1..3] 가변길이 탐색으로 2~3차 연쇄를 추적 (RDBMS JOIN depth 회피)
  • 뉴스는 bge-m3로 임베딩해 매일 HDBSCAN으로 이슈를 묶고 Claude가 라벨링, 이슈 centroid를 코사인 유사도(0.80)로 이어 붙여 며칠에 걸친 흐름(토픽 스트림)을 추적
  • 탐색·근거·클러스터 조회를 FastMCP 도구로 노출, Claude가 탐색 깊이와 tier·확신도를 직접 판단
결과
  • 고유 상장기업 3,038개, 공급망 관계 69,369건의 그래프 구축
  • 매일 Discord로 수혜주 리포트를 받아 실제 투자 판단에 활용 중
  • 홈서버에서 직접 운영 중

Project 02 · Triplan

여행 일정 설계 시, 환율·날씨·경보 정보를 사용자가 직접 찾아 종합해야 했던 문제 해결

자연어 기반 그룹 여행 플래너

GitHub

담당PM · RAG 파이프라인 설계 · 데이터 파이프라인 구축 · AWS 배포
흐름도
입력·출력핵심 처리데이터 저장
문제 원인
  • 여행 계획은 환율·날씨·여행경보·후보지 정보를 사용자가 따로 찾아 종합해야 한다.
  • LLM 단독 답변은 최신 정보와 근거가 약하다.
해결 과정
  • 환율·날씨·경보·유튜브를 Airflow DAG 4종으로 미리 수집 → PostgreSQL에 적재해 에이전트가 도구로 조회
  • 여행 영상 403개를 pgvector에 임베딩해 RAG 검색, 결과가 없으면 YouTube → 네이버 블로그 → GPT 생성 순으로 폴백
  • OpenAI function calling tool-calling agent가 일정 추가·수정·이동·삭제·장소 추천 등 도구 15개를 선택 실행
  • 입력은 프롬프트 인젝션 패턴 필터, 출력은 시스템 프롬프트 유출을 재검증
결과
  • 팀 프로젝트 2등 (SK네트웍스 AI 캠프 15기 최종 프로젝트)
  • 5인 팀 PM으로 RAG 파이프라인 설계·데이터 파이프라인·AWS 배포 담당
  • AWS EC2 7대 마이크로서비스 배포 — VPC 퍼블릭/프라이빗 서브넷 분리, 보안 그룹 4단계(Nginx→Frontend/Backend→DB)로 접근 통제
  • 4종 데이터 파이프라인과 영상 403개 임베딩 적재까지 구축, 배포 후 실시간 시연
실제 배포 아키텍처
입력·출력핵심 처리데이터 저장

그 외 연결: Django API ↔ Redis(캐시 R/W) · WebSocket ↔ PostgreSQL(쿼리) · Airflow → Django API(파이프라인 결과 전달)

Project 03 · Lecture-RAG

강의록 질의응답 시, LLM이 강의에 없는 함수·모듈을 만들어내던 환각 문제 해결

이원 청킹과 사후 검증으로 환각을 막은 강의록 질의응답 시스템

GitHub
2025.08 – 2025.096인 팀 · PM
담당PM · 이원 청킹·토큰 화이트리스트 검증 로직 설계 · AWS 배포
흐름도
입력·출력핵심 처리데이터 저장
문제 원인
  • ChatGPT에 강의록 관련 질문을 하면 강의에 없는 함수·모듈로 예제를 만들어낸다.
  • 프롬프트로 "강의 내용만 써라"고 지시해도 환각이 잡히지 않았다.
해결 과정
  • 헤더 기준 분할 + detect_code_blocks()로 코드 블록을 독립 청크로 보존
  • 강의록에 실제 존재하는 토큰을 extract_allowed_tokens()로 화이트리스트화, 답변 생성 후 사후 검증
  • 위반 토큰을 지목해 1회 재시도, HuggingFace 로컬 임베딩(all-MiniLM-L6-v2)으로 비용 제거
결과
  • 프롬프트만으로 안 잡히던 환각을 사후 검증으로 차단
  • 강의 외 함수명 차단 동작 확인, 로컬 임베딩으로 임베딩 비용 0원
  • Streamlit 프로토타입 → Django REST + PostgreSQL + Nginx + Docker Compose로 AWS 배포까지 확장, 팀 PM 담당

Project 04 · Gorochi

주문 응대 시, 픽업 안내와 품절 처리를 매번 수동으로 반복하던 문제 해결

지인의 케이크샵을 위해 기획부터 배포까지 1인 개발한 온라인 주문 서비스

gorochi.org
2026.07 – 현재1인 개발배포 완료 · 도입 준비 중
담당기획 · 설계 · 개발 · 배포 전체
흐름도
입력·출력핵심 처리데이터 저장
문제 원인
  • SNS DM 주문마다 픽업 시간·메뉴·결제 안내를 수동으로 반복해야 했다.
  • 품절 처리도 사람이 매일 직접 초기화해야 했다.
해결 과정
  • 슬롯 기반 주문으로 안내를 주문 화면에서 처리하고, 주문이 들어오면 관리자에게 SSE로 실시간 알림
  • 관리자가 서버로 스트림을 보낼 일이 없어 WebSocket 대신 SSE를 선택해 구현 단순화, 연결 인증은 30초 일회용 토큰
  • AsyncIO 크론 태스크가 매일 자정 품절 상태를 자동 초기화
  • PG 결제 연동
  • 부하테스트로 동시 접속 한계를 확인하던 중 SQLAlchemy 커넥션 풀 고갈(pool_size=5, max_overflow=10)이 병목임을 코드에서 확인, pool_size=20, max_overflow=30으로 조정
결과
  • 기획·개발·배포 1인 완료 — gorochi.org 배포, 실매장 도입 준비 중
  • 품절 초기화 수작업 제거, 카카오 로그인 + 전화 인증으로 본인 확인
  • 부하테스트(홈서버 4vCPU·47GB RAM): 커넥션 풀 조정 전 동시 접속 50명이 한계(그 이상 타임아웃) → 조정 후 동시 150명까지 무오류 처리 (약 3배 개선), CPU 사용률 1% 미만으로 여유 확인
